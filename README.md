# @ach/ui-kit

Общая дизайн-система: токены, контролы и composables одним пакетом.

Живёт отдельно от приложений, чтобы граница «дизайн-система ↔ продукт» была
физической, а не договорённостью.

## Потребители

| Проект   | Путь               |
| -------- | ------------------ |
| docta.me | `../docta.me/nuxt` |
| svad     | `../svad/site`     |

**Набор токенов один на все продукты, тем нет.** Это решение, а не недоделка:
свести облик проектов к одному было дешевле, чем поддерживать бренд-слой, —
у svad фирменный синий заменён на индиго, нейтральные сведены к slate-шкале.
Если однажды понадобится второй бренд, механизм тот же, что и для тёмной темы:
`--kit-color-*` начинают ссылаться на `--kit-brand-*`, а значения приезжают файлом темы.

Правя токен, помните, что он меняет **оба** сайта.

## Установка

В npm-реестр пакет не публикуется — ставится прямо из git:

```jsonc
// package.json приложения
{
	"dependencies": {
		"@ach/ui-kit": "git+https://github.com/aichukanov/ui-kit.git#main",
	},
}
```

Точный коммит пинуется в `package-lock.json`, поэтому `npm ci` на сервере
детерминирован. `file:../../ui-kit` для этого не годится: пути наружу
репозитория на сервере не существует и сборка падает. Для локальной работы
над пакетом используйте `npm link`, а не правку `package.json`, — подробности
и процедура деплоя в `docs/rules/DESIGN_SYSTEM_PACKAGE.md` у docta.me.

```ts
// nuxt.config.ts
export default defineNuxtConfig({
	modules: ['@ach/ui-kit/nuxt'],

	// Пока в проекте есть Element Plus — явной строкой, чтобы её было
	// видно и можно было удалить вместе с ним
	css: ['@ach/ui-kit/element-plus-bridge.css'],
});
```

Приложение НЕ должно объявлять `--kit-color-*`, `--kit-spacing-*` и прочие токены
у себя: они приезжают из пакета. Если такой блок где-то остался, он молча
перебьёт дизайн-систему — именно так svad и разошёлся с docta.me.

В Less-проекте цветовые переменные можно свести к токенам
(`@primary-color: var(--kit-color-primary)`), но только если в коде нет
Less-функций над цветом (`darken`, `lighten`, `fade`) — они падают на
строке `var(...)`. Отступы так не переводятся: Less не считает арифметику
по CSS-переменным.

Модуль сам подключает токены в начало цепочки CSS и регистрирует компоненты
и composables автоимпортом. Дальше `<KitButton>` и `useToast()` работают
без единого импорта.

Пакет отдаётся **исходниками** (`.vue`, `.ts`), сборки нет: их компилирует Vite
приложения. Поэтому нет ни шага сборки, ни расхождения `dist` с `src`.

## Что внутри

|                                      |                                                                            |
| ------------------------------------ | -------------------------------------------------------------------------- |
| `src/styles/tokens.css`              | Токены: цвета, типографика, отступы, радиусы, тени, z-индексы              |
| `src/styles/element-plus-bridge.css` | Временный мост `--el-*` → токены; подключается **явно** в `css` приложения |
| `src/components/`                    | Контролы `Kit*` — автоимпорт                                               |
| `src/composables/`                   | `useToast()` — автоимпорт                                                  |
| `src/icons/`                         | Универсальные иконки — **явный** импорт                                    |
| `nuxt/module.ts`                     | Nuxt-модуль: CSS, автоимпорты, transpile                                   |

## Правила

**Токены — единственный источник значений.** В стилях компонента не должно быть
ни одного hex, px-цвета или магического отступа. Исключения помечаются
комментарием с причиной. Благодаря этому тёмная тема — это второй набор
значений в `tokens.css`, а не правка компонентов.

**Контраст.** Каждое состояние держит WCAG AA: 4.5:1 для текста, 3:1 для
границ и иконок. Значения в `tokens.css` подписаны замеренным контрастом —
меняя цвет, пересчитайте и обновите комментарий.

**Ни одной строки на конкретном языке.** Все видимые тексты и `aria-label`
приходят пропсами или слотами. За i18n отвечает приложение.

**SSR-безопасность.** Никаких обращений к `window`/`document` вне `onMounted`.
Разметка на сервере и на клиенте должна совпадать.

**Иконки: только универсальные.** Стрелки, крестики, галочки, спиннеры — здесь.
Логотипы мессенджеров, «клиника», «врач», «анализ» — предметная область
приложения, им место в нём. Автоимпортом иконки пакета не регистрируются —
импортируйте их явно: набор мелкий, а лишние глобальные имена ради шести
SVG не нужны. Раньше причиной была коллизия с `Icon*` приложения; после
перехода на префикс `Kit` её нет, но и повода регистрировать не появилось.

## Именная конвенция

Всё, что принадлежит дизайн-системе, несёт префикс **`kit`**. Приложения
оставляют себе `app-*` для своих компонентов. Правило существует ровно для
того, чтобы в devtools и в коде было видно, чей это элемент: раньше
`app-button` (ДС) и `app-header` (приложение) выглядели одинаково.

| Что                              | Пример                                                             |
| -------------------------------- | ------------------------------------------------------------------ |
| Компоненты                       | `KitButton`, `KitAlert`                                            |
| CSS-классы                       | `.kit-button`, `.kit-button__icon`, `.kit-button--variant-primary` |
| Токены                           | `--kit-color-primary`, `--kit-spacing-lg`                          |
| Внутренние переменные компонента | `--kit-button-fill`, `--kit-alert-line`                            |
| Иконки                           | `KitIconClose`                                                     |
| Имена переходов                  | `kit-toast`, `kit-loading-fade`                                    |

Исключение одно: **`useToast()`** имя не меняет. Конкурирующего `useToast`
ни в одном приложении нет, а `useKitToast` в 45 местах вызова не добавил бы
ясности — только шума.

Токены под префиксом сознательно, хотя это дороже всего (3000+ мест в двух
проектах): без него `--color-primary` было не отличить от переменной
приложения, и вся затея теряла смысл на самом массовом уровне.

## Словарь пропсов

Один и тот же смысл называется одинаково во всех компонентах:

- `variant` — смысл: `default | primary | success | warning | danger`.
  У `KitAlert` варианты названы по событию (`error` — «ошибка произошла»),
  а не по опасности действия. Это разные вещи и разные слова намеренно.
- `appearance` — вес оформления: `solid | plain | text | link`.
- `size` — `small | default | large`.
- `type` — **нативный** тип элемента (`button | submit | reset`), как в HTML.
  В Element Plus `type` означал вариант оформления, из-за чего в проекте
  встречались `<el-button type="submit">`, молча не отправлявшие форму.

Классы модификаторов пишутся с префиксом измерения —
`kit-button--variant-default`, `kit-button--size-default`: без него значения
`default` у варианта и у размера дают один класс.

## Компоненты

| Компонент           | Заменяет      | Назначение                                                  |
| ------------------- | ------------- | ----------------------------------------------------------- |
| `KitButton`         | `el-button`   | Кнопка                                                      |
| `KitAlert`          | `el-alert`    | Сообщение о состоянии в потоке страницы                     |
| `KitTag`            | `el-tag`      | Неинтерактивная метка. Кликабельная метка — это `KitButton` |
| `KitSkeleton`       | `el-skeleton` | Заглушка на месте загружающегося контента                   |
| `KitEmpty`          | `el-empty`    | «Ничего не найдено»                                         |
| `KitLoadingOverlay` | `v-loading`   | Вуаль над блоком, который перезагружается на месте          |
| `KitToaster`        | —             | Хост тостов, монтируется **один раз** в `app.vue`           |
| `useToast()`        | `ElMessage`   | `success` / `error` / `warning` / `info`                    |

`useToast()` можно вызывать откуда угодно, включая обработчики событий
и `.catch()`: стек не привязан к setup-контексту. На сервере тосты
отбрасываются — показывать их там некому, а в HTML они бы мигнули при гидрации.

## Проверка

Своих `node_modules` у пакета нет и не должно быть: единственная зависимость —
`vue`, и второй её экземпляр на диске ломает реактивность и `provide/inject`.

> **Ловушка:** `npm link`, запущенный в папке пакета, ставит peer-зависимости
> и создаёт здесь `node_modules` с собственным `vue`. Глобальная регистрация
> линка от этого не зависит, поэтому сразу после `npm link` эту папку нужно
> удалить: `rm -rf node_modules`. Симлинк в приложении продолжит работать —
> `vue` для файлов пакета TypeScript находит через `paths`, которые дописывает
> Nuxt-модуль.

Проверки запускаются **из приложения-потребителя** — оно и так тянет файлы
пакета в свою программу TypeScript:

```powershell
cd ../docta.me/nuxt
npm run typecheck                              # включая файлы пакета
npx prettier --write "../../ui-kit/**/*.{ts,vue,css,json,md}"
```

Чтобы `vue` разрешался в файлах пакета, Nuxt-модуль сам добавляет `paths`
в сгенерированный `tsconfig.json` приложения — см. комментарий в `nuxt/module.ts`.
